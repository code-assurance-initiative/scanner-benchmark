# Watchdog baseline — scanner-benchmark iteration 1 (2026-10-07)

## 1 Purpose and scope

This document records how Watchdog performed on the scanner benchmark **before any improvement work**. Every later
engine version is compared against it, so it is frozen. It covers all 25 registered benchmark repositories at their
latest registered tags (15 C#, 10 TypeScript). It also covers every one of the rubric's 154 in-scope dimensions,
grouped by the catalog's ten lenses. The 11 out-of-scope dimensions are listed where the run produced a row for them.

- Machine-readable freeze: [`baseline-2026-10-07.json`](baseline-2026-10-07.json).
- Generator: [`baseline.py`](baseline.py) (standard library plus the in-repository `cai_bench`). It re-scores every
  repository in process from its key at the tag and from the SARIF that was scored. If the re-score differs from
  [`final-scores.json`](final-scores.json) in any way, it aborts. Every table below sits between
  `<!-- BEGIN/END baseline:… -->` markers and is that script's output (`python3 results/watchdog/baseline.py
  --update-doc results/watchdog/BASELINE-2026-10-07.md`; `--check` fails when the doc or the JSON is stale).
- The prose is the analysis. The tables are the data.

## 2 Instrument and method

| | |
|---|---|
| Scanner | Watchdog, kennel `main` **6a05dfb6c**, rubric **rubric-2026.10.1** |
| Mode | **contained**: analyzer image `codehealth-analyzer:train-src-89d1e8def87553cc` (gitleaks, semgrep, trivy, checkov, osv inside; deny-by-default egress), via `tools/multilang/scan.py --contained` |
| Configuration | scanner **default**. No compliance framework, no `--with-llm`, no runtime evidence |
| Harness | `cai_bench` 1.3.1, contract 1.4, mapping `mappings/watchdog.json` (rubric-2026.10.1) |
| Keys | `git show <tag>:benchmark/answer-key.json`; sha256 equals `registry.json` for all 25 |
| Lenses / names | rubric catalog snapshot (kennel `engine/rubrics/rubric-catalog-snapshot.json`), identical to `coverage/matrix.json` |

**Metrics (contract 1.4).** Recall = TP / (TP + FN) over planted `must-fire` entries. Trap resistance = traps left
alone / traps (`must-not-fire`). Noise share = noise results / all results of the concepts the key covers. File-level
recall is secondary: a plant counts as found when a result of its concept lands anywhere in its file.

**What counts as noise.** A result is noise in any of these four cases:

- it lands on a trap (`trap-fp`);
- it lands in a certified-clean region (`clean-fp`);
- it is of a concept the key declares not applicable (`na-fp`);
- it is of a covered concept and matches no entry within ±3 lines (`unmatched-fp`, written "unl" for unlabelled
  below).

A second result on a plant that was already found is `redundant` (neither a hit nor noise). A location-less roll-up
that the mapping declares a summary is `summary-of-concept` (also neither). Results of concepts the key does not cover
are `uncovered` and are never counted as noise.

**Per dimension vs per lens.**

- A dimension row is the harness's own per-dimension row, summed over repositories. Matching is re-run inside the
  dimension. A plant is counted under **every** dimension its concept maps to. For example, a hard-coded credential
  counts under D13, D28, D29 and D31. Dimension rows therefore overlap: the plant counts sum to 626, not 384.
- "FN missed by run / found by other dim" splits a dimension's FNs into two groups. The first group is plants that
  no dimension found. The second is plants that another dimension found.
- A lens row counts each plant and trap **once per lens**. It uses the per-concept rows: a concept belongs to every
  lens one of its dimensions belongs to, and a plant is found when the run found it. Results and noise are the sum of
  the lens's dimension rows. Every result has exactly one dimension, so the lenses partition the results exactly
  (558 results, 280 noise).

**Caveats.**

1. **IaC line-1 noise.** checkov reports every Kubernetes check at line 1 of the manifest. trivy reports pod-level
   checks on the workload's `spec` line. The harness therefore calls those rows noise, and some plants become FNs
   that were found in the file. D31 has 83 noise rows out of 99 (13 on traps, 18 in clean regions, 52 unlabelled). The
   authoring triage judged 35 of the final-scan rows `redundant` (they restate a planted defect) and 29
   `opinion-not-fact`. D31's file-level recall is 46.4 %, against 32.1 % by line.
   `bench-csharp-security-iac` alone carries 60 of the 280 noise rows. Without it, noise is 220/475 (46.3 %).
2. **Location-less rows.** 191 of the 750 SARIF rows in the 25 final scans have no location. Three contract
   additions recover them where the row names its site: 18 TPs by `subject`, 8 repository-level and 1 from the
   message. Where the row does not name its site, the plant stays an FN and the row is noise or summary-of-concept.
   D23's 64 unlabelled noise rows, D36 workflow rows and X2 roll-ups are examples.
3. **Unmapped concepts count as FN.** The taxonomy is scanner-neutral. 15 plants of 11 concepts that no Watchdog rule
   maps form the `(no scanner rule)` row. 4 more plants are of mapped concepts for which the mapping holds no evidenced
   rule: `pointless-catch-rethrow` → X3, `excessive-mocking` → D10, and `unchecked-any-external-data` → R1 (×2).
   Together these are the 19 "no rule for the concept" FNs. They are real defects Watchdog cannot see, not harness
   artefacts.
4. **Model-judged dimensions are not measured in the headline.** 16 dimensions are `llm`-evaluated (D19–D22, D24,
   D25, DM8, ED5, ES3, LA1–LA6, M4). The contained fence denies the model host, so they compose only in host
   `--with-llm` passes, which are a secondary measurement (`hostModelPass` in `final-scores.json`). Their plants are
   FNs here: D25 0/2, M4 0/1, LA2 0/2, LA5 0/2, LA6 0/1. 73 of the 144 unscored bands sit on them.
5. **Model non-determinism** (section 10.1). Bands on model-judged dimensions are single observations.
6. **Out-of-scope dimensions.** AXR1 (runtime, rendered accessibility) shows 0/19 by construction: no static scan
   composes it, and AC1–AC6 carry the same plants. It is listed, but it is excluded from every ranking.

What the lens table says:

- **Security (57.5 %) and Readiness (57.3 %) have the most absolute misses** (57 and 35 FNs). The causes are SAST
  taint and sinks, prefix-less secrets and repository-wide posture switches. Security also carries the most noise
  (109 rows, mostly D31 line-1 rows).

  rule, D23, which takes each project for a bounded context.

- **Maturity is mostly unmeasured in the contained headline.** Its model-judged dimensions are absent: 64 of its 99
  bands are unscored.
- **TypeScript lags in every lens that has a C# counterpart, except Accessibility.** The gaps are Code Health (52 %
  vs 85 %), Domain Modelling (44 % vs 82 %), Readiness (45 % vs 69 %) and Security (49 % vs 64 %).

## 5 Per dimension

Every in-scope dimension, one table per lens.

- **Repos** = the number of repositories whose key labels the dimension (any label, including clean, not-applicable
  and band) or in which it produced a result.
- **FN missed by run / found by other dim** splits the dimension's FNs as described in section 2.
- **Noise trap/clean/NA/unl** gives the kinds of noise.
- **File rec.** is shown only where it differs from recall (= means equal).
- **Bands** gives the score bands read from this dimension.
- **◆** marks a model-judged dimension (not composed in the contained default scan).

Under each table, the **main miss mechanism** is the commonest curated FN mechanism among the plants no dimension
found (the [`summarise.py`](summarise.py) classification). The **main noise mechanism** is the largest backlog item
filed for the dimension, measured by sites over all authoring iterations. The backlog id is truncated; full ids are in
section 9. Where no item was filed, the cell gives the authoring verdicts of the final-scan noise rows.

## 11 Re-measuring against this baseline

A later engine is comparable only when these four things hold:

- the same 25 keys (same tag and the same key sha256; `compare` warns otherwise);
- contained mode;
- default configuration;
- a mapping updated for any new rule ids (`mappings/watchdog.json`; the harness version may change).

Run one scan at a time, because there is one box-wide scan slot. Scan full-history clones, because D28, D15, D16, D34
and D35 read history. The 25 units live in the training set
[`training-set-2026`](https://github.com/code-assurance-initiative/training-set-2026) as git bundles (full history,
every tag); the unit repositories this baseline was first scanned from are retired. Materialise every unit from its
bundle (into a directory named exactly after the unit, outside any git work tree), scan, re-score, compare:

```sh
WS=~/RiderProjects/cai-bench                   # workspace: _scans, _rescans, materialised units
SB=$WS/scanner-benchmark
SET=$WS/training-set-2026                      # git clone https://github.com/code-assurance-initiative/training-set-2026

"$SET/tools/verify.sh"

cd "$SB"

      --repo-dir "$WS/_frozen/$LABEL/$name" --out "$WS/_rescans/$LABEL/$name") || echo "SCAN FAILED: $name"
done

# 2. score every scan against its key at the tag (key read from the materialised unit, sha256 checked against the
#    baseline) -> a final-scores.json of the same shape. Without --units-dir the keys are read straight from the
#    set's bundles (--set-dir, default: training-set-2026 next to scanner-benchmark).
```

`tests/test_compare.py`.
